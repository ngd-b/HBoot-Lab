# HBoot-Lab #024｜为了排查错误，我没有把请求内容写进日志

最近，我在给统一 AI 能力平台补审计日志。

这个平台接在几个产品和外部服务之间。一次调用失败，用户看到的可能只有一句“服务器异常”。到了后台，我想知道的是：这是哪一次请求，走了哪个接口，最后停在哪里。

最省事的办法，是把收到的请求和返回结果都记下来。

以后出问题，打开日志一看，什么都有。

但做到参数校验失败时，这个问题就绕不过去了。

这个平台以后处理的，可能是一张图片、一张票据、一段语音，也可能是用户写下的一段话。请求里还可能带着 Cookie、认证信息和查询参数。

如果把这些内容全部记下来，日志确实更好查了。

可用户只上传了一次内容，后台却悄悄多保存了一份。原本是为了排错，最后又多造出一个需要保护的地方。

所以我把范围收了回来。

现在留下的是请求 ID、操作者、接口类型、状态码、耗时和整理过的错误信息。管理员拿到请求 ID，可以在后台找到这一条记录，也可以只看失败请求。

请求正文和响应正文不记。

Cookie、Authorization 和查询参数也不记。

参数没通过校验，只留下“参数校验失败”这类提示，不把用户刚提交的内容抄进审计表。

写到这里，还有一个问题。

业务失败时，数据通常会回滚。但如果审计记录也跟着一起回滚，最需要找原因的时候，反而什么都没留下。

所以审计单独写入。业务可以失败，失败这件事本身要留下来。

反过来也一样。

一次正常请求已经完成，不能因为审计数据库刚好出问题，又向用户返回失败。日志没写进去，服务端会留下请求 ID 和异常类型，但不会改变原来的处理结果。

我也没有把所有请求都塞进去。

成功的只读请求很多，大部分时候没有排查价值。全部记录，只会让真正重要的失败和修改更难找到。

这次我没有把“完整”理解成，把用户提交过的东西再复制一遍。

用户带着一个请求 ID 来，我能找到那次失败；同时打开日志的人，看不到他的图片、文字和凭据。

对现在这个阶段来说，这些信息刚好够用。

## 发布依据

- unified-ai 仓库提交 `a4d7d6ef`（2026-09-19）新增请求审计与控制台审计查看器，记录写操作和失败请求，并支持按请求 ID、操作者、操作类型及“只看失败”筛选。
- 请求审计记录请求 ID、接口模板、HTTP 状态、耗时和错误摘要；不采集请求正文、响应正文、Cookie、Authorization 或 URL 查询参数。
- 参数校验失败测试验证用户提交的敏感输入不会进入审计记录；未处理异常测试验证异常消息中的敏感内容不会进入记录或响应。
- 审计使用独立数据库事务，业务回滚不删除失败记录；审计写入失败时保留原接口结果，只输出包含请求 ID 和异常类型的服务端错误日志。
- 成功的只读请求和 OPTIONS 请求不写入请求审计，避免低价值记录淹没失败和变更。
- 正文描述的是已经进入仓库并通过对应测试的行为，不声称该功能已经上线生产环境，也不声称已经减少故障或缩短排查时间。
