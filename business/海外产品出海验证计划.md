# 海外产品出海验证计划

- 状态：待验证
- 核心目标：用最少改动验证陌生海外用户是否愿意为 HBoot 的现有能力付费
- 产品顺序：Receipt Web 产品 → Obsidian 插件 Pro
- 当前原则：先完成一次真实收款，再抽象统一 Billing / Entitlement 服务

## 一、这次验证什么

这次不同时重做两个产品，也不先建设完整的海外 SaaS 基础设施。

第一阶段只验证一件事：

> 有没有陌生海外用户愿意为一次明确的任务支付 5 美元。

Receipt 产品先验证海外 Web 支付、Credits 和英文获客闭环。验证成功后，Obsidian 插件再复用已经跑通的支付与授权能力。

执行顺序：

```text
Receipt 英文 Landing Page
        ↓
免费处理 10 张票据
        ↓
Paddle Checkout（候选）
        ↓
第一笔陌生用户付款
        ↓
Credits 与购买权益稳定运行
        ↓
Obsidian 插件接入 Pro 授权
        ↓
出现第二个真实使用方后，再评估抽离 Billing / Entitlement
```

Paddle 只是当前支付候选。正式接入前需要重新核对中国大陆个人或现有主体能否注册、支持的结算方式、税务处理、退款和争议规则，以及所售数字产品是否符合平台要求。

## 二、产品一：Receipt → Excel / CSV

### 产品定位

海外版不再强调“智能记账”，只解决一个直接任务：

> Turn receipts into clean Excel or CSV in seconds.

第一批目标用户：

| 用户 | 当前麻烦 | 第一版价值 |
| --- | --- | --- |
| Freelancer | 报销和小票需要手工录入 | 批量转成 Excel / CSV |
| Small business | 每月需要整理几十到几百张 receipt | OCR、分类、检查和导出 |
| Accountant / VA | 替多个客户整理凭证 | 批量上传和结构化 CSV |

第一阶段不接 QuickBooks，不做银行同步、自动报税、完整财务系统或复杂团队协作。

### 可复用的现有能力

现有“小票智能分类记账”已经具备：

- JPG、PNG、PDF 批量上传
- OCR 与结构化字段提取
- 发票、小票、支付记录和交通票据类型识别
- 分类、搜索、筛选和字段编辑
- Excel / CSV 导出
- Web 管理台和异步处理队列

因此第一版重点不是重写识别系统，而是英文包装、字段边界、支付和获客闭环。

### 第一版用户流程

```text
Drop your receipts here
        ↓
自动识别并区分文档类型
        ↓
用户检查和修正字段
        ↓
Export CSV / Excel
```

首页只突出上传、处理进度、人工检查和导出，不堆叠自然语言查账等其他能力。

### 字段边界

不要强行让所有单据共用一套 Schema。先按文档类型分别处理：

| 类型 | 第一版字段 |
| --- | --- |
| Receipt | Merchant、Date、Total、Tax、Currency、Category |
| Invoice | Invoice number、Supplier、Tax ID、Date、Total、Tax、Currency、Category |
| Payment proof | 第一版只保留实际能够稳定识别和导出的字段，不能套用 Invoice 专属字段 |

导出时允许不同类型使用不同列，或让用户按类型分别导出。正式开发前需要基于现有数据结构确认兼容方案。

### 第一阶段收费

第一阶段先卖 Credits，不要求用户订阅：

| 套餐 | 建议价格 |
| --- | ---: |
| Free | 10 receipts |
| 100 receipts | $5 |
| 500 receipts | $15 |
| 2,000 receipts | $39 |

Credits 是否永久有效、失败任务是否退回、重复文件是否计费，需要在付款前明确展示。

只有出现重复购买后，再判断是否增加 Subscription。不要在尚未验证复购前先建设复杂套餐系统。

### 名称与域名

第一阶段不急着购买新域名，可以先使用：

`invoice.hboot.fun`

候选产品名均为暂定：

- ReceiptSheet
- ReceiptFlow
- Receipt2CSV

先用功能型名称测试转化，不为品牌命名延迟上线。英文首页默认使用 English。

### 第一轮获客

优先建设搜索意图明确的 Landing Page：

- `/receipt-to-excel`
- `/receipt-to-csv`
- `/invoice-to-excel`
- `/receipt-ocr`
- `/expense-receipt-scanner`

每个页面只回答对应任务，不批量生成内容相近的空壳 SEO 页面。

Reddit、X 和产品演示使用一个容易看懂的前后对比：

> I had 57 receipts.
>
> Instead of typing them into a spreadsheet, I dropped them here.
>
> 40 seconds later: clean CSV.

其中“57 receipts”和“40 seconds”只能在真实演示达到后使用；没有实测前改成实际数据，不作为固定宣传话术。

演示素材：

- 上传前：一批经过脱敏的 receipt
- 处理中：批量识别进度
- 导出后：字段清楚的 Excel / CSV

### 验证漏斗与成功标准

第一轮不以注册量为主要指标，记录完整漏斗：

```text
有效 Landing Page 访问
        ↓
开始上传
        ↓
完成一次识别
        ↓
完成字段检查或导出
        ↓
用完免费额度
        ↓
打开 Checkout
        ↓
完成购买
```

第一阶段成功标准：

> 100 个有效访问中，有用户完成上传、跑完免费额度，并出现第一笔陌生海外用户购买。

判断边界：

- 有第一笔陌生用户购买：继续优化识别、导出和购买转化。
- 有上传和免费使用，但没有购买：先检查免费额度、价格、导出价值和 Checkout 阻力。
- 500～1000 个精准访问后仍无人购买：暂停扩功能，重新检查用户定位和付费任务是否成立。
- 没有上传：优先检查流量是否精准、首页表达和样例是否可信，不把问题误判为价格问题。

“有效访问”和“精准访问”的统计口径需要在投放前定义，至少排除机器人、内部访问和明显无关流量。

## 三、产品二：Obsidian → Local AI Sync

### 产品定位

这个产品面向开发者和知识管理用户，不按大众工具的方式推广。

长期定位：

> Keep your Obsidian vault synced with your local AI knowledge base.

AnythingLLM 是第一个 Backend，不作为长期产品边界。后续是否增加 Open WebUI、Dify、自建 RAG 或 Custom API，由真实用户需求和付费情况决定。

当前已具备的基础能力：

- Obsidian Plugin → AnythingLLM
- 新建和修改监听
- 自动同步
- Folder 配置

### Free / Pro 边界

让用户先免费确认同步确实有用，再为减少重复操作付费。

| Free | Pro |
| --- | --- |
| AnythingLLM | Multiple backends |
| 手动同步 | Real-time sync |
| 1 folder | Multiple folders |
| 基础日志 | Sync history |
| 基础过滤 | Advanced ignore rules |
| — | Retry failed sync |
| — | Multiple workspaces |

最重要的付费边界：

> 手动同步免费，自动同步收费。

用户可以先完成安装、配置和一次手动同步，确认价值后再决定是否购买 Pro。

### 第一阶段定价

- Free：基础手动同步
- Pro：$19 lifetime，作为早期价格

只有在功能、持续维护成本和真实付费需求得到验证后，再评估提高到 `$29 / $39 lifetime` 或改为订阅。价格变化不对已有用户追溯收费，具体权益以购买页面说明为准。

### 最小授权链路

长期可以复用统一认证，但第一版不先建设复杂 License Server。

最小链路：

```text
Paddle Purchase
        ↓
purchaseId → license entitlement
        ↓
插件输入 License Key 或登录
        ↓
服务端 validate
        ↓
开启 Pro
```

第一版只需要解决购买、签发、验证、撤销和退款后的权益失效。离线宽限、设备数量、License 转移和风控策略，根据真实问题再增加。

### 第一轮获客

优先渠道：

- GitHub
- Obsidian Community
- Reddit
- X
- 插件文章与 Obsidian Market 页面

核心演示不讲架构，直接展示：

```text
编辑 Obsidian 文件
        ↓
AnythingLLM 中对应内容自动更新
```

可使用的内容方向：

> I got tired of manually re-uploading my Obsidian notes into AnythingLLM.
>
> So I built an Obsidian plugin that keeps them synced automatically.

发布时只描述已经实现并验证的同步行为，不提前宣传尚未接入的 Backend。

## 四、公共能力的演进顺序

目标架构可以是：

```text
                 auth.hboot.fun
                       │
        ┌──────────────┴──────────────┐
        │                             │
 Receipt Web                  Obsidian Plugin
        │                             │
        └──── billing / entitlement ──┘
                       │
                    Paddle
```

但这不是第一阶段的开发顺序。

正确顺序：

1. Receipt 产品直接接入一个最小 Checkout。
2. 完成第一笔真实付款、Credits 发放和退款处理。
3. Obsidian 插件需要相同能力时，再识别重复部分。
4. 第二个产品完成接入后，才评估抽成独立 Billing / Entitlement 服务。
5. 统一认证只承载身份，不在需求出现前扩张成完整商业平台。

## 五、明确暂时不做

- 不同时重做两个产品
- 不先开发 `billing.hboot.fun`
- 不先做复杂 License Server
- 不为 Receipt 接 QuickBooks、银行同步或自动报税
- 不先做月度订阅
- 不为 Obsidian 插件一次接入多个 Backend
- 不先购买新域名或花大量时间确定品牌名
- 不用注册量、点赞或内部测试付款替代陌生用户真实购买
