# 一拍成图

## 状态

**⏸ 已记录，计划后续开发（2026-08-29）**

当前只保留产品设想、技术路线和服务边界，不进入代码开发，也不加入当前项目列表。

项目工作名称：**一拍成图**

项目英文标识：`snap-to-image`

## 产品设想

把纸张、白板或黑板上的文字、线条和手绘内容拍下来，自动整理成干净、可保存、可打印的电子图片。

核心流程：

```text
拍照或选择图片
→ 调整四角
→ 选择纸张 / 白板 / 黑板 / 画作模式
→ 自动矫正和净化
→ 预览与简单调整
→ 保存高清图片或生成打印版
```

可能服务的场景包括：

- 学生拍摄板书、公式、思维导图和手写笔记，整理后保存或打印
- 教师保存板书、黑板报和课堂示意图，继续制作教学资料
- 家长和孩子把纸质画作转换成干净线稿，重新上色并保存
- 普通用户把纸面草图、流程图或临时记录转换成清晰图片

产品定位不局限于儿童画，也不承诺理解或重新生成图片内容。第一阶段只负责把真实拍摄内容矫正、清理和导出。

## 建议 MVP

第一阶段优先验证净化和打印，不同时完成所有画作编辑能力。

- 微信小程序拍照和相册选择
- 手动选择纸张、白板或黑板模式
- 自动检测边缘并进行透视矫正
- 用户拖动四个角兜底
- 去阴影、增强对比度、灰度和黑白处理
- 黑板内容反色为适合阅读和打印的白底图片
- 原图与处理结果对比
- 简单的清晰度和细节保留调节
- 保存高清 PNG
- 生成 A4 打印版

画作模式作为后续验证：

- 提取和平滑线稿
- 修复小范围断线
- 识别封闭区域
- 使用区域蒙版在小程序 Canvas 中点击上色
- 必要时允许用户手动补线，避免填色泄漏

首版不做 OCR 搜索、自动内容总结、生成式上色、复杂 SVG、批量扫描和长期云端画册。

## 技术架构

产品后台和关键图像能力保持分离：

```text
微信小程序「一拍成图」
          │
          ▼
一拍成图业务后台（Python + FastAPI）
          │
          ▼
统一能力服务平台
    ├── 产品与服务注册
    ├── 服务鉴权与路由
    ├── 按产品统计调用量
    ├── 限流、健康检查和审计
    └── 能力版本管理
          │
          ▼
独立图像处理服务（Python + FastAPI）
    ├── OpenCV
    ├── NumPy
    ├── Pillow
    └── 后续按需增加 Potrace / CairoSVG
```

统一能力服务平台与统一认证平台职责分离：

- 统一认证平台管理用户身份、登录和产品授权关系
- 统一能力服务平台管理产品调用服务的关系、路由和用量
- 两个平台可以共享基础设施，但不合并业务职责和数据模型

## 服务边界

### 一拍成图业务后台负责

- 微信小程序业务接口
- 产品内用户、任务和作品记录
- 用户级额度、历史记录和结果保留策略
- 向统一能力服务平台发起处理请求
- 把处理结果组织成产品页面需要的数据

### 统一能力服务平台负责

- 产品注册、能力注册和调用凭证
- 根据能力名称和版本选择实际服务
- 按产品记录调用次数、耗时、成功率和资源用量
- 统一限流、超时、重试、熔断和健康检查
- 不保存一拍成图的用户资料、作品关系和其他产品业务数据

### 图像处理服务负责

- 透视矫正、去阴影、对比度增强和黑白转换
- 黑板内容增强与反色
- 线稿提取、断线修复和区域蒙版生成
- 高清 PNG 和打印文件渲染
- 算法尽量保持无状态，只通过签名文件地址或临时对象读取输入和返回结果
- 不依赖一拍成图的用户表、任务表和产品规则

计划注册的能力可以包括：

```text
image.document.correct
image.document.clean
image.board.clean
image.drawing.extract-line-art
image.drawing.detect-regions
image.export.print
```

这些能力以后可以由小票归类、图片处理工具或其他产品复用，不为一拍成图提供专用接口。

## 数据与文件边界

- 产品后台保存用户、作品和业务任务关系
- 图像服务通过短期签名地址获取原图，不接收产品用户身份
- 统一能力平台只记录产品标识、能力名称、请求标识、结果状态、耗时和资源用量
- 临时处理文件设置自动过期时间，最终作品由产品后台决定是否长期保存
- 日志不记录图片内容、签名地址和用户敏感信息

## 图像处理路线

纸张和白板：

```text
缩放
→ 纸张或内容区域检测
→ 透视矫正
→ 光照与阴影归一化
→ 灰度化
→ 自适应二值化
→ 去噪
→ 输出高清图片
```

黑板：

```text
缩放
→ 透视矫正
→ 背景和粉笔线条增强
→ 对比度调整
→ 黑白反转
→ 输出白底打印图
```

画作：

```text
净化图片
→ 提取线稿
→ 小范围形态学闭运算
→ 识别封闭区域
→ 生成区域蒙版
→ 小程序 Canvas 上色
→ 导出 PNG
```

第一版图片最长边限制在 2048px，直接使用同步 HTTP 处理。出现明显排队、超时或并发压力后，再增加 Redis 队列和独立 Worker。

## 技术可靠性边界

以下能力相对成熟，可以作为第一阶段重点：

- 纸张和白板的透视矫正
- 去阴影、灰度、黑白增强和打印导出
- 清晰黑板内容的增强与反色

以下场景需要限制输入或提供手动兜底：

- 严重反光、遮挡、模糊或角度过大的黑板照片
- 很浅的铅笔线、彩色复杂画、水彩和密集素描
- 存在大量断线的儿童画封闭区域填色
- 需要忠实保留全部笔触细节的复杂线稿矢量化

产品不承诺所有图片一键成功。自动裁切失败时允许手动调整四角，净化结果允许调节清晰度，区域填色失败时允许补线。

## 开发前验证

正式开发小程序前，先单独制作 Python 图像处理原型：

- 收集不同手机、光线和角度拍摄的真实样本
- 纸张、白板、黑板和手绘图分别准备测试集
- 验证矫正后内容是否完整
- 验证处理结果在手机阅读和 A4 打印时是否清楚
- 记录失败类型，而不是只保留效果好的样本
- 先证明多数目标图片无需调整，失败图片可以手动修正，再开始完整小程序开发

## 主要风险

1. 扫描和文档增强已有成熟替代品，只有处理效果不一定形成长期差异化。
2. 教师、学生和家庭场景虽然可以共享底层能力，但主要需求不同，产品入口过多会让第一版难以理解。
3. 黑板反光、残留粉笔印和低对比度字迹会导致效果不稳定。
4. 传统区域识别无法保证所有儿童画都不漏色，必须提供手动修正。
5. 保存和打印可能是低频行为，需要验证用户是否会处理第二张图片，而不只是第一次觉得新鲜。
